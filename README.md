# Kadai4_ToDolist（提出課題④ 進捗管理ボード / Nuxt版）

タスクを登録して、期限とステータスで進捗を管理するアプリ。
提出課題①（素のJavaScript）と同じ題材を、Nuxtで作り直す。

## 技術スタック

| 種別           | 使用技術                                                        |
| -------------- | --------------------------------------------------------------- |
| フレームワーク | Nuxt 4（`ssr: false` / 実PJT準拠）                              |
| UI             | Vue 3（Composition API / `<script setup>`）                     |
| 言語           | TypeScript                                                      |
| 状態管理       | Pinia（`@pinia/nuxt`）                                          |
| Node           | 24.22.1（`.node-version` / `.nvmrc` で固定）                    |
| 公開           | GitHub Pages（main へのマージで GitHub Actions が自動デプロイ） |

## セットアップ

```bash
nvm use        # .nvmrc の 24.22.1 に切り替える
yarn install
```

## 開発コマンド

| コマンド        | 内容                                              |
| --------------- | ------------------------------------------------- |
| `yarn dev`      | 開発サーバーを起動する                            |
| `yarn generate` | 静的ビルド（GitHub Pages に公開されるものと同じ） |
| `yarn preview`  | ビルド結果をローカルで確認する                    |

## リポジトリ構成

```
.github/workflows/deploy.yml  main へのpushでビルドしGitHub Pagesへ公開
app/
  assets/styles/tokens.css    デザイントークン（色・余白・角丸・影）
  pages/                      ページ。ファイル名がそのままURLになる
nuxt.config.ts                ssr:false / Pinia / baseURL などの設定
public/                       静的ファイル（ビルドされずそのまま配信される）
```

## スタイルの決まり

- 色・余白・角丸・影は `app/assets/styles/tokens.css` のCSS変数を `var(--…)` で参照する。値を直書きしない
- コンポーネントのスタイルは `<style scoped>` に閉じる

## 公開フロー

main にマージされると `.github/workflows/deploy.yml` が動き、`yarn generate` の出力（`.output/public`）が GitHub Pages に公開される。
サブパス配信のため `nuxt.config.ts` の `app.baseURL` をリポジトリ名から自動で決めている。

### 【STEP1】

- Pinia使い方<br>
  Udemyの動画を視聴しなおす。<br>
  - store<br>
    composableのようなもの。1ストアに1機能を実装する。<br>
  - DefineStore()<br>
    Piniaが必ず持つ関数。第一引数にそのストア名、第二引数に処理をする関数を書く。必ずreturnを返す。returnはオブジェクトである必要があり、第二引数で宣言したすべてのconstを持たなければならない。<br>
  - 命名規則<br>
    use【任意】Store<br>
  - 使用するには<br>
    component内で呼び出し、use【任意】Store()で使える。<br>
    `.オブジェクト名`で利用でき、`.value`不要。どこからでも変更可能な値。<br>
    **【追記】「どこからでも変更可能な値」ではあるが、「どこからでも変えてよい値」ではない。**
  - state<br>
    ストア内で定義されたrefオブジェクト。必ずreturnに乗せる<br>
  - getter<br>
    ストア内で定義されたComputedRefオブジェクト。<br>
  - Action<br>
    ストア内で定義された関数。<br>

- Piniaとcomposableをどう使い分けるか<br>
  どこまでがPiniaに乗せて実装すべきかでご相談。結論として、どこからでも呼び出したいデータをPiniaに持たせ、その操作や表示はcomponentに分離。<br>
  - 見た目、操作の二種類に分けることは今までと変わらない。
  - タスク管理のUI＝ユーザーの操作なので同じ箇所でよい。

- Task、Statusの型作成方法<br>
  作成の際は前回課題のインターフェイスを参照。実装方法としてidとセレクトボタンの利用も考えたためご相談<br>
  - idとセレクトボタンで管理する→並べ替えの機能を実装する必要がある時には楽（日本語のソートは設定が面倒）
  - stringでは幅が広すぎる→三パターンだけで制限を強くすることでほかの値が入るようなエラーを防ぐ。

- 特定の内容しか持たない型の設定方法<br>
  ①配列自体をタイプにする→増減するなら。動的に変わる場合。例）その配列を別で管理しているなど
  ②UNION形で宣言→絶対に変更されない。見やすい。例）降順昇順、選択肢が少なくて固定になる値
  書き方の違いがあるだけで、配列で持っていたとしてもやることはユニオン型だったり→配列からユニオン型を作るイメージ

- 日付の形成<br>
  フォームでカレンダーをクリックする形式になると考え、課題①を参照。<br>
  前回からの変更点としては、arrow関数を利用することで変数を一つ減らし、Piniaとしての戻り値も減らしている。

### 【STEP1　返却時】

- 各コンポーネントに持たせる機能<br>
  返却時にご指摘いただいた。修正前は、TaskListが表示、TaskItemがその機能の本体と考え実装していた。
  - TaskList<br>
    タスクの一覧表示。データの受け渡し、0件時のエラーメッセージ、繰り返し処理はここで行う。<br>
    子コンポーネントを呼び出す際にv-forを付与。
  - TaskItem<br>
    タスクの一行単位。日付の成型、各項目を横並びに`<tr>`化、削除ボタンの実装はここ
  - TaskForm<br>
    タスクの入力フォーム
    という構成。

- storeに登録する内容<br>
  返却時のご指摘。もともと、storeの中にlimitDate(現formatDate)が入っていた。<br>
  storeに保持する値の条件は、

  > 置き場所の目安は「データを変えるかどうか」です。
  >
  > - データそのものと、データを変える処理（追加・変更・削除の action）→ ストア
  > - データは変えず、どう見せるかだけの処理（日付の整形など）→ 表示するコンポーネント
  >   となる。上記のように、今回日付の成型は元データに対して行うものではなく、ユーザーの表示のための機能なのでstoreに含めず、一行単位の表記を担うTaskItemに格納。

- component名<br>
  必ずパスカルケース。

- v-forとkey属性<br>
  v-forで配列などを回す際は、予期せぬバグを防ぐため必ずkey属性を付与する。
  その際、key属性は一意な値でなけらばならないため、今回はidを追加した。

- 命名の変更<br>
  ローカル上でGUIに頼り操作しても、**その変更が大文字・小文字の区別の場合は**git上に反映されない。反映させるためには、<br>
  **git mv 元ファイル名　新ファイル名**<br>
  と入力する必要がある。<br>
  なお、文字そのものを変える（task.vueからtaskList.vueなど）の場合はGUIでも反応する。

- `<nav>`<br>
  ユーザーが目的のページにスムーズに移動できるよう配置する、ナビゲーションリンクを実装するためのタグ。<br>
  今回、`.nav a{}`という風にaタグにスタイルを指定しているが、これは`<NuxtLink>`が`<a>`タグに変換されるためである。

- `<tr>`<br>
  `<table>`内で`<thead>`,`<tbody>`を作ること、`<tr>`の配下に`<td>`を置くことは認識していたが、`<thead>`の`<th>`にも`<tr>`を置くことを失念していた。<br>
  `<tr>`で横の行を作り、その中を`<th>`や`<td>`によってセルを作り区切っていくイメージを持つ。

- オブジェクトの設定<br>
  当初、コンストラクタ関数を利用し、毎回同じ型でユーザーの入力値に応じたオブジェクトを成型しようとしていた。しかしながら今回の場合、Taskインターフェイスで入力できる型に制限がかかっているので、わざわざコンストラクタ関数を利用せずともオブジェクトリテラルで毎度作成するのみでよい。<br>
  【追記】interfaceの型は、JavaScriptへの変換時に消えてしまう（＝実行時には何もチェックしない）が、TypeScriptで書いているときには間違いをエディタが示してくれる<br>
  →その恩恵を受けるには、オブジェクトを型のついた場所に入れる必要がある（＝「型を使た場所に入れる」のが大事なところ）

- @submit.prevent<br>
  動作確認時にsubmitで画面がリロードされてしまうため検索。<br>
  JSにおけるevent.preventDefault()と同じ効果を持つ。フォーム送信時の画面遷移を自動で止める。<br>
  今回のようにメソッド名を付与することで、フォーム送信時の画面遷移を止めながら、そのメソッドを実行することができる。

### 【STEP2 フィードバック】

- storeの管理<br>
  storeの目的は、「データが変わる入り口を一か所にまとめる」ということには変わりない。しかしながら、STEP2提出時点では、そのデータを作るための部品であるtaskName、taskDate、statusといった項目がstore内にあり、エラーメッセージの表示もstore内のaddTaskに担わせる内容となっていた。以下、頂いた詳細解説より整理した内容<br>
  - **フォームの入力値をstoreではなくcomponentで持つのはなぜか。**<br>
    →storeの目的は、本体のデータとそれが変わる入り口を一か所にまとめること。今回であれば、本体とはtaskArray配列のことであり、その内容を追加・変更・更新するものをstoreにまとめることが適切。（=taskArray配列は、トップページでも利用）
    - v-modelによる同期を行い、一文字入力するごと、またフォームのリセットごとにもtaskFormのref（下書き）を変更。最終的にaddTask()を実行した回数分だけのデータがstoreにわたる。
    - taskName, taskDate, statusの三項目は、あくまでもtaskArrayを構成するための部品であるためcomponentへ。一方、idだけはcomponentに管理を任せると、ページ移動のたびにrefがリセットされ、常に一意とする管理ができなくなってしまう。そのため、taskArrayの中にあるaddTaskで管理する。
    - ストア内にtaskName, taskDate, statusといった項目を設定すると、その中身の値がどれを指すのかを読み手に考えさせてしまう。
  - **「追加」を押すと、どのデータがどの順番で変化するのか**<br>
    1. TaskForm: submitが起こると、submitTask()が呼ばれる
    2. TaskForm(): submitTask()内のtrim()で空のバリデーション調査（もし空なら、TaskForm: alert表示しreturn→入力値は残存）
    3. TaskForm: addTask()を呼び出す
    4. store: addTaskの中でidを付与しpush, 次回用にidを++
    5. TaskList: 画面に描写、TaskForm: 下書き（taskName, taskDate, status）が初期値に戻る
  - **AddTaskに引数で内容を渡すと何が良くなるか**<br>
    可読性の向上、エラー表示。addTaskに引数がないと、読み手側からすれば実際にaddTaskに何を送っているのかが不明瞭となる。（idの付与をstore内のaddTaskで行っているので、タスク一件当たりの全貌が余計にわかりづらくなる。）さらに、引数を渡すことで型チェックも行えるようになる。

- `Omit<Task,"id">`<br>
  参照元（Task）の型から特定のプロパティ（id）を除外し新しいオブジェクト型を作る。

  > idはストアが付けるので、呼ぶ側（フォーム）はidを渡せない。渡さなくてよい、ということを型で表しています。

- `{...task.id:taskId.value}`<br>
  storeのaddTaskで利用する。

  > スプレッド構文。taskの中身(name・limit・status)をそのまま並べて、そこにidを足した新しいオブジェクトを作ります

  ```js
  <!-- 引数には、idをのぞいたTask型のオブジェクトtask -->
  const addTask = (task:Omit<Task, 'id'>)=>{
    <!-- スプレッド構文を使い、オブジェクトの結合を行う -->
    taskArray.push(...task, id:taskId.value)
    taskId++
  }
  ```

- min属性
  `<input type="date">`に付与することで、指定した日付以前の日付を選択できなくなる。課題③で学んだ、本日の日付を文字列で取得する`.toLocaleDateString`と組み合わせ利用する。実装するかどうかはSTEP4にてご相談
