# Kadai4_ToDolist（提出課題④ 進捗管理ボード / Nuxt版）

タスクを登録して、期限とステータスで進捗を管理するアプリ。
提出課題①（素のJavaScript）と同じ題材を、Nuxtで作り直す。

## 技術スタック

| 種別           | 使用技術                                                        |
| -------------- | --------------------------------------------------------------- |
| フレームワーク | Nuxt 4（`ssr: false` / 実PJT準拠）                              |
| UI             | Vue 3（Composition API / `<script setup>`）                     |
| 言語           | TypeScript                                                      |
| 状態管理       | Pinia（`@pinia/nuxt`）                                          |
| Node           | 24.22.1（`.node-version` / `.nvmrc` で固定）                    |
| 公開           | GitHub Pages（main へのマージで GitHub Actions が自動デプロイ） |

## セットアップ

```bash
nvm use        # .nvmrc の 24.22.1 に切り替える
yarn install
```

## 機能概要

<!-- TODO: 何ができるアプリか、画面と操作を書く -->

ユーザーがフォームに入力した値をToDoリスト化し、一覧表示する。<br>
一覧表示した内容は、未対応・処理中・完了の三つのステータスを変更でき、削除もできる。<br>
共通の機能としてヘッダーを持ち、このヘッダーではに画面の行き来ができる。

### `/` トップページ

機能：タイトル、このアプリの概要が表示されており、画面下部の「タスク一覧へ」の文字を押下すると、`/tasks`に移動することができる。

### `/tasks`　タスク一覧

機能：画面上部の入力フォームに各要素に入力し、「追加」ボタンを押下するとタスクを追加することができる。追加した内容は画面下部の「タスク一覧」に表示され、状態の変更、削除が行える。<br>
**入力フォーム各機能**<br>
各機能、項目名をクリックするとカーソルが入力枠を選択するようになっている。<br>

- タスク名<br>
  ユーザーの文字入力をタスク名として受け取る。入力は必須であり、空欄や空文字で登録しようとするとアラートが表示される。アラート表示後も、各項目の入力値はフォームに保持される。<br>
- 期限<br>
  日付を選択できる。初期値はこのアプリを使用している時点の日本の日付となっている。<br>
- ステータス<br>
  「未対応」「処理中」「完了」の三種類のみから選択できる。初期値は「未対応」<br>
  <br>
  **タスク一覧各機能** <br>
- タスク名、期限<br>
  入力値が反映されている。タスク名は不要な空欄が削除された状態で表示されており、期限はYYYY/MM/DDの表示になっている。<br>

- ステータス<br>
  初期値はユーザーがフォームで入力した値が選択されている。プルダウン式で「未対応」「処理中」「完了」のステータスが変更されるようになっており、一度トップページへ遷移しても変更した値は保持されている（変更に応じて実データも変更しているため）<br>
- 操作<br>
  ゴミ箱の画像が付いたボタン。クリックすると、その列のデータを削除することができる。ステータス同様、実データを変更するためトップページへの遷移を行っても、消したデータは削除されたままになっている。

### 【STEP1】

- Pinia使い方<br>
  Udemyの動画を視聴しなおす。<br>

  - 命名規則<br>
    use【任意】Store<br>
  - 使用するには<br>

    `.オブジェクト名`で利用でき、`.value`不要。どこからでも変更可能な値。<br>

### 【STEP2 フィードバック】

- storeの管理<br>
  storeの目的は、「データが変わる入り口を一か所にまとめる」ということには変わりない。しかしながら、STEP2提出時点では、そのデータを作るための部品であるtaskName、taskDate、statusといった項目がstore内にあり、エラーメッセージの表示もstore内のaddTaskに担わせる内容となっていた。以下、頂いた詳細解説より整理した内容<br>
  - **フォームの入力値をstoreではなくcomponentで持つのはなぜか。**<br>
    →storeの目的は、本体のデータとそれが変わる入り口を一か所にまとめること。今回であれば、本体とはtaskArray配列のことであり、その内容を追加・変更・更新するものをstoreにまとめることが適切。（=taskArray配列は、トップページでも利用）
    - v-modelによる同期を行い、一文字入力するごと、またフォームのリセットごとにもtaskFormのref（下書き）を変更。最終的にaddTask()を実行した回数分だけのデータがstoreにわたる。
    - taskName, taskDate, statusの三項目は、あくまでもtaskArrayを構成するための部品であるためcomponentへ。一方、idだけはcomponentに管理を任せると、ページ移動のたびにrefがリセットされ、常に一意とする管理ができなくなってしまう。そのため、taskArrayの中にあるaddTaskで管理する。
    - ストア内にtaskName, taskDate, statusといった項目を設定すると、その中身の値がどれを指すのかを読み手に考えさせてしまう。
  - **「追加」を押すと、どのデータがどの順番で変化するのか**<br>
    1. TaskForm: submitが起こると、submitTask()が呼ばれる
    2. TaskForm(): submitTask()内のtrim()で空のバリデーション調査（もし空なら、TaskForm: alert表示しreturn→入力値は残存）
    3. TaskForm: addTask()を呼び出す
    4. store: addTaskの中でidを付与しpush, 次回用にidを++
    5. TaskList: 画面に描写、TaskForm: 下書き（taskName, taskDate, status）が初期値に戻る
  - **AddTaskに引数で内容を渡すと何が良くなるか**<br>
    可読性の向上、エラー表示。addTaskに引数がないと、読み手側からすれば実際にaddTaskに何を送っているのかが不明瞭となる。（idの付与をstore内のaddTaskで行っているので、タスク一件当たりの全貌が余計にわかりづらくなる。）さらに、引数を渡すことで型チェックも行えるようになる。

- `Omit<Task,"id">`<br>
  参照元（Task）の型から特定のプロパティ（id）を除外し新しいオブジェクト型を作る。

  <!-- 引数には、idをのぞいたTask型のオブジェクトtask -->
  const addTask = (task:Omit<Task, 'id'>)=>{

  }
  ```

  // 通常の配列の宣言のように、型を三つ用意し、末尾にas constを付けることでreadonlyなリテラル型を用意

  export type Status = (typeof STATUSES)[number];
  ```

- セレクトボタンの入力値を送信する方法<br>
  STEP3第一回PR時点では、`<select :value="○○">`と指定することで`<select>`の入力値を別の場所に送れると考えていた。しかしながら、`<select>`につけるvalueには、`<option>`につける場合と違い、初期値として見た目の指定はできても実際の値を加工できるわけではない。これを理解していなかったことが、STEP3の手戻りの原因となった。解説資料を頂戴したこと、ご相談により解消。<br>
  <br>
  以下、頂いた解説資料の「１，この資料のゴール」をもとに疑問点と理解を記載する。<br>
  - `:value="newStatus"`の形では、選んだステータスがストアに届かないのはなぜか<br>
    `<select>`につける`:value=`の値は、表示を変えるのみで実データを持つわけではないため。

  - 行のステータスをTaskItemの`ref`にコピーして持たない方がよいのはなぜか（PR2のフォームの下書きとの違い）<br>
    今回の場合、すでにstore内で形成されているデータのコピーを変更することにあたるため。二か所に同じデータがあり、片方を変更してももう片方がそのままになってしまうなど、値のずれが発生しうる。原則として、**refに持ってよいのは「まだストアにない、確定前の値」** である。<br>

  - 選んだ値を保持せず、その場でactionに渡すと、値がどの順で流れるか<br>
    ①プルダウンでの選択肢に別のものを選択すると、onChangeStatusが発生する<br>
    ②onChangeStatusにて引数として、変更される該当のtaskおよび、event.target as HTMLSelectElementにてセレクト属性の選択値が、storeのchangeStatusに送信される。<br>
    ③storeのchangeStatusにて、実際に該当の値が変更されtaskArrayが書き換えられる<br>
    ④taskArrayの値が書き換わったことで、それをもとに表示を行っていたTaskListでの表示も更新される<br>
    以降、変更があるたびに①から④を繰り返す<br>

- (event:Event)が引数の関数<br>
  ~~引数が(event:Event)の場合、Vueが自動で判断し対象のイベントを引数としてくれるため、関数を利用する際でも()が不必要。~~
  **【追記】**
  引数が(event:Event)だから不必要なわけではなく、関数を利用する際に()を付けなかったため、Vueが自動で判断し対象のイベントを第一引数としてくれている。もし()を付けて関数を記述していれば、指定がないのでeventがundefinedとなり、動作しなくなる。この場合、引数に($event)を渡すとVueが本来自動で行うイベントの用意を明示的に指示できる。

- as HTMLSelectElement<br>
  TypeScriptでは、引数にEventを用いた際にはそのEventが何を指しているのかを明示する必要がある。今回であれば、HTMLの`<Select>`が対象となるためこの形となる~~（指定しなければstringなどと解釈されてしまう）~~。プリミティブ型を指定するわけではないため注意。
  **【追記】**

  > 指定しなければstringなどと解釈されてしまう
  > は誤り。もともとevent.targetはTypeScriptで`EventTarget | null`に受け取られる。この`EventTarget`は「イベントを受け取れる何か」という大きな型であり、それにas HTMLSelectElementで、`<select>`であると伝えている。ここで初めて、select.value(string型)が使えるようになる。先のPRであったように、asは型チェックの時のみ働き、JSにコンパイルする際には特に意味をなさない。
